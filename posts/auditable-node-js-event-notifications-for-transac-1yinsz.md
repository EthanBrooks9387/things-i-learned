# Auditable Node.js Event Notifications for Transactional Email and SMS Report Fallback

Choose the design that can reconstruct which generated report left the system, where it went, and why a second channel fired. For an edtech report attachment, that means a Node.js evidence ledger beside the notification worker: email first, status polling as a bounded observation mechanism, and SMS escalation only under a versioned policy. Transport acceptance alone is too weak for the compliance record.

| Choice | Evidence produced | Main gap | Operating burden |
|---|---|---|---|
| Email with no status observation | Attempt and attachment identity | No later transport state | Low |
| Email with polling | Attempt, attachment identity, observed state | Evidence arrives on the poll schedule | Moderate |
| Email with policy-driven SMS escalation | Cross-channel timeline and escalation reason | More recipient data and duplicate-contact risk | Higher |

Recommendation: use the third design only when the notification policy has a real deadline. Otherwise, email plus polling is the better default. **The attachment hash, policy version, and append-only transitions are the durable evidence; the provider response is one event in that record.**

## How should Node.js event notifications track transactional email before SMS fallback?

Start with the audit question, not the channel API. A school may need to show that a particular generated report was submitted to an address under a particular policy. It may instead need evidence that the destination system accepted the message, or that an authorized person viewed the report. Those are three different claims. The first is an application event, the second is a transport event, and the third belongs at the authenticated report boundary.

Keep them separate.

Consider an illustrative policy, not a universal timeout. A report is generated at 09:00, its digest and policy version are committed, and the email submission is accepted at 09:01. A poll at 09:06 still sees a deferral. If that policy sets escalation at 09:30, the worker records the observation and schedules another bounded step; it does not send a text early merely because one poll was inconclusive. If delivery appears at 09:24, the evidence closes the escalation path. If the deadline arrives with no delivery observation, one leased worker sends the generic SMS and records why. This timeline forces reviewers to name the exact event that satisfies the obligation, and it exposes a common modeling error: using the time a worker happened to poll as if it were the time a transport event occurred.

For each notification, record an internal ID, a report version, a SHA-256 digest of the exact attachment bytes, a policy version, a destination fingerprint, and timestamps generated by your own system. Each transport attempt then appends its channel, external message ID, observed state, provider timestamp when supplied, and ingestion timestamp. A digest can show that retained bytes have not changed relative to the recorded value. It cannot establish that the report was correct or that the recipient read it.

The first decision criterion is therefore claim strength. An `accepted` response means the transport accepted the submission. Do not rename it `delivered`. A poll can later observe a delivery, deferral, or permanent failure state exposed by the chosen transport, but application access still needs its own event.

The second criterion is disclosure surface. Email carries the generated attachment, so authorization, address accuracy, retention, and report content already matter. SMS adds a phone number and another path to a recipient. NIST SP 800-63B treats the public switched telephone network as a restricted authenticator; a text notification should not become proof of identity. Keep student details out of the message, and require authentication before a text link reveals a report.

## Build the ledger before the poller

The expensive failure isn't a slow poll. It is an ambiguous record after a retry. A worker can submit an email, lose its process before persisting the response, and then run again. Polls can return the same state repeatedly. Two workers can cross an escalation deadline together. These cases are ordinary distributed-system boundaries, so the data model needs idempotency and a lease before the happy path gets polished.

Use one append-only event vocabulary across channels, while preserving the raw channel state separately. The normalized vocabulary answers business questions. The raw value keeps the adapter debuggable. Do not force every provider state into a misleading universal sequence.

DMARC is useful in a different layer. RFC 7489 defines domain-level handling based on SPF and DKIM authentication identifiers, alignment, policy, and reporting. That evidence helps operators assess whether mail uses the intended domain controls. It does not prove report receipt or report access. Store authentication observations without promoting them to a human-read signal.

For a one-person SaaS, this boundary is worth defending. Outsource transport. Keep the policy clock, evidence schema, authorization decision, and audit query in the application, because those pieces encode the obligation and change with the business. That is the revenue-per-hour trade: integrate commodity delivery once, then spend weekly shipping time on the report workflow users actually touch.

## Implement one bounded Node.js transition

The following TypeScript models a single scheduled worker invocation. It does not hold a request open while waiting. A durable queue schedules another observation, and a lease prevents concurrent escalation. The example uses generic adapters because the state transition matters more than any transport SDK.

```ts
type ObservedState = "accepted" | "deferred" | "delivered" | "failed";

type ReportNotice = {
  id: string;
  reportSha256: string;
  emailMessageId: string;
  phone: string;
  policyVersion: string;
  escalateAt: Date;
};

interface EmailStatusReader {
  get(messageId: string): Promise<{
    state: ObservedState;
    observedAt: Date;
    rawState: string;
  }>;
}

interface SmsSender {
  send(input: {
    idempotencyKey: string;
    to: string;
    body: string;
  }): Promise<{ messageId: string }>;
}

interface EvidenceLedger {
  appendOnce(event: {
    key: string;
    noticeId: string;
    channel: "email" | "sms";
    state: string;
    externalId: string;
    occurredAt: string;
    policyVersion: string;
  }): Promise<void>;
  withLease<T>(noticeId: string, work: () => Promise<T>): Promise<T>;
}

async function observeOrEscalate(
  notice: ReportNotice,
  email: EmailStatusReader,
  sms: SmsSender,
  ledger: EvidenceLedger,
  now: Date,
): Promise<"complete" | "poll_again" | "escalated"> {
  return ledger.withLease(notice.id, async () => {
    const status = await email.get(notice.emailMessageId);

    await ledger.appendOnce({
      key: `email:${notice.emailMessageId}:${status.state}`,
      noticeId: notice.id,
      channel: "email",
      state: status.state,
      externalId: notice.emailMessageId,
      occurredAt: status.observedAt.toISOString(),
      policyVersion: notice.policyVersion,
    });

    if (status.state === "delivered") return "complete";
    if (status.state !== "failed" && now < notice.escalateAt) {
      return "poll_again";
    }

    const sent = await sms.send({
      idempotencyKey: `report-notice:${notice.id}:sms`,
      to: notice.phone,
      body: "A new report is available. Sign in to view it.",
    });

    await ledger.appendOnce({
      key: `sms:${sent.messageId}:accepted`,
      noticeId: notice.id,
      channel: "sms",
      state: "accepted",
      externalId: sent.messageId,
      occurredAt: now.toISOString(),
      policyVersion: notice.policyVersion,
    });

    return "escalated";
  });
}
```

The worker returns `poll_again`; the queue decides the next execution time. Backoff, a maximum observation window, and the escalation deadline belong in the versioned policy rather than in scattered timers. A new policy must not silently reinterpret an old notification.

No hidden timer.

There is one sharp edge in this compact example. If SMS accepts the submission and the process stops before `appendOnce`, a retry reaches the sender again. The idempotency key asks the adapter to reconcile that uncertainty, but its exact guarantee depends on the transport contract. Where the adapter cannot provide a durable idempotency guarantee, persist a send intent and reconcile uncertain outcomes instead of claiming exactly-once delivery.

## Test the timeline, not just the adapter

Use a controllable clock and test event orderings. A concise suite should cover a delivery observation before the deadline, repeated deferrals, permanent failure, delivery after escalation, duplicate poll results, two workers reaching the deadline, and a stop between transport acceptance and local persistence. Assert the final ledger, not merely the return value.

Operations should follow the same model. Measure the age of the oldest unfinished notification, time between local submission and each observed state, notifications beyond their policy deadline, lease contention, duplicate-event conflicts, and escalation counts by policy version. Keep email addresses, phone numbers, attachment names, and signed links out of metric labels and routine logs. An internal notification ID is enough to join a trace to controlled evidence storage.

Reconstruction is the release test. Given one notification ID, an authorized operator should be able to state which report digest was involved, which policy applied, what each channel reported, when the application learned it, and whether authenticated access occurred. If the query needs raw log searching or human interpretation of several dashboards, the compliance mechanism is unfinished.

Ship this in narrow slices: one report type, one policy version, one audit query. Then add another state only when it changes a decision. A large taxonomy built ahead of an obligation consumes the same week that could improve report generation or recipient access.

## When is the simpler option better?

Email with polling is the runner-up, and it is better when a delayed or failed email does not create a time-bound duty to contact the recipient another way. It keeps the attachment evidence and observed transport state while avoiding phone-number collection, SMS disclosure risk, and cross-channel races. Email without polling is reasonable only when the required claim stops at a documented submission attempt and the transport contract supports that interpretation.

Immediate email and SMS may fit an independently defined urgent-notice policy, but it should not emerge from a retry shortcut. It intentionally creates two contacts. Record that policy choice as such.

Polling itself is appropriate when the integration cannot accept callbacks or the workload does not justify another authenticated ingress. Its limitation is repeated requests and observation delay. Event callbacks reduce that delay and repeated work, but require authentication, deduplication, and asynchronous handling at a public receiver. The ledger-and-fallback approach is not suitable when the organization has no time-bound escalation duty, cannot keep phone ownership current, or cannot justify storing another recipient identifier; choose email with the smallest evidence scope that satisfies the stated obligation. **Neither mechanism upgrades acceptance into delivery or delivery into human access.** The evidence claim remains the design anchor.
